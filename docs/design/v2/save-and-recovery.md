# v2 保存、结束与恢复

状态：文件、可靠保存和生命周期原则已确定；全领域字段、物理清理图、容量与工程采用
仍未完成。本文不激活 archive format 2，也不改变 v1 的 16 MiB/近期历史/只读导出合同。

## 文件与独立覆盖证明

目标为单个非 ZIP、严格 UTF-8 JSON 战役文件，候选外壳包含 `fileKind=CAMPAIGN`、
`formatVersion=2`、`campaign`、精确规则三元组 `module` 和类型化 `partitions`。
最终字段随未发布全域模型协调设计，不要求兼容旧内部 DRAFT 片段。

文件保存战役稳定身份、业务事件尾、角色初始/当前状态、完整进度和全部已记录业务历史。
不包含规则内容、本地行 ID、run/snapshot、row version、Host epoch、N/W、请求收据、
档案键/保存序列、结束代次、凭据或技术日志。AUTO 与 FINAL 使用相同业务外壳，本地用途
不赋予文件额外执行或删除权限。

应用为准确文件格式和规则发布定义封闭的必需分区集合，不由输入自报、非空表或当前已实现
分区推导。缺项、未知、重复、畸形值、范围溢出和悬空引用都拒绝。空数组只能表达一个已
完整实现且实际无行的分区，不能代替尚未实现的角色、法术或历史。

每个字段必须有源所有者、文件落点或明确排除理由、直接恢复映射及独立期望。先验证源到
文件全覆盖，再核对严格读取后的恢复投影；不能仅靠 writer/reader 往返相等。恢复直接写
入已验证的状态与历史，不重执行事件，不补造历史，不自动完成回合或重置资源。

## 档案与结束事实

档案区与工作集同属运行数据库，但生命周期独立。候选、不可变正式产物元数据、真实字节、
结束绑定、接受收据及字节移除事实职责分开。档案组按稳定战役键组织，保存序列由服务端
单调分配；产物键不复用，删除字节不撤销原接受事实或重定向旧键。

一个运行最多一次逻辑结束。初次 FINAL 是第 1 代；修复产生新产物和新代次，原基线与原
END/REPAIR 收据不可改写。当前可用性、原接受事实和清理完成是不同结论。

## 最终保存 A、清理 B 与修复 C

| 阶段 | 必须做什么 | 失败时保留什么 |
|---|---|---|
| A：最终保存 | 在共同守卫下捕获最新完整源，验证可直接恢复；一个事务保存 FINAL 字节、首代结束和接受收据，形成禁止游戏写入的待清理事实 | 没有任何 DELETE；保留工作集、快照、候选和旧档 |
| B：独立验证与清理 | 新事务重读已提交 FINAL，验证完整恢复语义及与原工作集等价，按完整依赖图删除本次工作集/快照/临时控制及合格候选；同时记录清理、释放绑定、推进 epoch 并核对计费 | 任一失败回滚整个 B；不撤销已提交 FINAL，不继续删半套 |
| C：坏最终档修复 | 仅在原工作集完整未变且当前 FINAL 确证损坏时，创建新的不可变产物/代次，原子推进绑定和计费 | 不改旧字节/收据、不删除、不恢复游戏；仍待独立 B |

内存编码成功、HTTP 200 或浏览器声明下载成功都不是 B 的依据。B 必须从数据库真实读回
已提交字节；全域入向外键、触发器、历史、领域待办和清理范围未盘点完整时，B 保持关闭。

正常 END 一次明确意图可以协调 A 后的一次独立 B，不需要正常流程再次确认。A/C 响应
不明、精确重放、提交查证、GET 和重启不会自动触发 B；故障恢复使用准确 run/ending/
代次/产物的新受保护继续意图。C 成功只接受修复，之后另行继续 B。

技术结束保存中途状态：未完成步骤、回合阶段、未决业务选择和已持久化准备材料都需如实
覆盖。它只排空在途数据库事务，不替用户结算效果、退出战斗、治疗、计步或改变剧情。
源规则、旧 v1、其他战役、永久身份登记、结果事实和已保存档案不属于工作集清理范围。

## 重启残留与显式删除

v2 重启不发布旧 ACTIVE 执行视图。核验依赖、精确身份、完整工作集、计费及旧事务已决后，
可以用同一个 END/A/B 协议救援最新残留；核验视图只授予保存能力。无法完整保存时保留
数据转独立维护，不提供启动清库、丢弃残留、取消结束继续游戏或旧 AUTO 覆盖源的捷径。

用户显式删除档案只在全工具真实空闲、无候选/残留/待清理/未决时接受，精确删除一个
archive key 的字节并记录移除和计费。产物元数据、身份、收据、结束/修复/清理事实永久
保留。最后一份本机文件需要明确的保管/丢弃意图；这不证明外部副本已存在。无自动过期、
后台清收据或“清空战役”批量入口。

## 容量与增长

| 工程验证基线 | 值与含义 |
|---|---|
| 单文件 | 64 MiB，原始输入和实际 UTF-8 输出均有界 |
| 档案文件逻辑预算 | 1 GiB，已占字节加尚未兑现预留不得超限 |
| 文件预警 | 已占与预留达到预算的 80% |
| 每运行结束预留 | 128 MiB，用于初次 FINAL 与首次修复各 64 MiB；AUTO 不可借用 |
| 元数据独立预算 | 每单位 4096 逻辑字节、16384 单位；保留事实不会随字节删除消失 |
| 可导出结构 | 深度 16、单数组 100000、总数组项 200000、值节点 2000000，另需逐字段界 |

这些是已选验证起点，不是压测结果、物理磁盘/堆内存承诺或最终发布容量。每个命令必须
在写前证明变化后仍可完整导出，并为不可删除的技术事实计费，不能先写入再发现无法保存。
候选复制、三份轮换、坏档及新修复产物的峰值分别核算，不截断历史或自动删用户档腾空间。
逻辑配额之外还须验证 InnoDB、日志、驱动、解析/编码及并发内存的实际峰值。

## 保管与灾备

可恢复业务文件需共同保管：文件真实字节、精确匹配的完整规则制品、实际支持它的已审
应用制品。逐份实际读回核验；同名、更高版本、摘要自洽或持有旧 WAR 都不自动取得恢复资格。

业务文件恢复与数据库灾备是两条路径。业务文件不恢复本地技术身份、请求结果或删除历史。
数据库回退/克隆还需两侧数据、外部配置及身份/接受/删除历史连续性证明，不能通过重置
epoch 获得新初始化资格。恢复演练和部署沿[备份恢复](../../backup-and-restore.md)、
[部署](../../deployment.md)的独立检查点执行，不因本设计自动运行旧应用或覆盖现库。
