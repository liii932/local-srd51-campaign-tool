# v2 采用边界

本文连接当前实现与 [v2 设计基线](README.md)。它记录稳定的差异、前置条件和暂缓范围，
不记录某次测试计数、数据库迁移成功或部署状态，不替代 GitHub 的实施任务。

## 当前实现与目标的区别

| 主题 | 当前仓库依据 | v2 目标与采用条件 |
|---|---|---|
| 正式规则 | 发布注册表仅允许 legacy v1 为默认 RELEASED | 完整规则族保持 DRAFT，统一发布门后才允许正式绑定和切换默认 |
| 规则读取 | 当前业务仍读取运行库的 `module_*` / DRAFT 目录 | 来源域表 → 完整本地快照 → 不可变执行视图；普通业务无来源能力 |
| 语言与工具目录链路 | 正式作者源、统一离线安装和来源 reader、V019/V020 运行镜像及独立等价测试源码 | 18 项语言、37 项工具熟练引用；分区基础可复用，不能扩称完整角色领域、启动就绪或游戏运行 |
| 目录形状 | 内部 DRAFT 使用 definition/attribute/relation 三表 | 按领域设计类型化物理表，不保留旧草稿兼容分支 |
| 纯规则模型 | `module.ModuleCatalog` 为唯一不可变投影；全部目录仓储与真实消费者共用 | 归属调整保持模型字段、集合不可变性及 v1 canonical 字节，不等于目录物理拆分 |
| 成长与恢复区间 | `module.AdvancementValueProfile` / `ResourceRecoveryProfile` 提供共用的文本与类型化不可变区间；目录、初始资源和升级逐级验证 1—20 级熟练加值，内部恢复组件按权威魅力值求值 | 尚未获得、无限或已满资源仍校验恢复区间；角色作者 schema、类型化来源表、运行镜像和完整休息事务仍须接入 |
| 旧诊断分层 | `web` 装配 JNDI/listener，`service.DatabaseDiagnostics` 编排，`persistence` 查询 schema | 原单库配置、逐请求复查及有限错误响应保持；两侧准备/执行诊断仍待采用 |
| 启动 | 现行服务可按调用读取目录，较早拆库方案提出多发布注册表 | 唯一所选规则准备视图；初始化前来源复核，导入后发布对应完整快照视图 |
| 角色 | 旧角色根/字段表和创建、成长等 DRAFT 切片 | 同 run/snapshot 的身份、初始卡、当前状态和全历史；逐领域补齐所有者 |
| 重启 | v1 从数据库恢复活动状态 | 新 v2 残留只供救援，不自动恢复执行资格；不改变 v1 |
| 存档 | v1 16 MiB、最多近期 50 条；DRAFT codec 只覆盖内部角色片段 | 完整业务/历史、独立源覆盖、可靠档案保存与受控结束；新容量不放宽 v1 |
| 事务 | 各现行 Service/部分 Repository 的既有事务实现 | 共同接纳与永久屏障先接入所有写入口，再逐命令采用调用方事务 |
| 运维 | 当前 JNDI、迁移和部署合同 | 双角色连接、最小权限、身份连续性及回退逐项验收，不能只换 WAR |

当前实现定位见[项目地图](../../agent-context.md)、[数据库](../../database.md)、
[语言链路核验](../../rules/language-partition-equivalence.md)及[格式 2 内部角色切片](../../rules/archive-format-2-character-state.md)。
表中的“已有”指仓库交付边界，不证明测试本次运行、迁移实际执行或功能已部署。

成长与恢复的纯规则校验不构成角色领域完整链路。该领域仍须将严格作者输入、离线投影与
安装、类型化来源读取、运行镜像及独立字段/字节期望连成同一条可验收链路。语言与工具
PARTITION 只能提供分区基础；全域必需目录、交叉引用及 COMPLETE 校验尚未完成，
不能据此开放新运行、完整存档或完整休息命令。

## 采用顺序

1. 建立共同的产品/目标设计入口，明确 v1、内部 DRAFT 和新模型的边界。
2. 复用语言作者、安装和两侧存储链路，逐领域补足作者 schema、领域表、快照及独立投影。
   纯模型已归入 `module` 并由真实消费者共用，不复制兼容模型。
3. 完成外层装配、诊断和准备/执行能力分离；新旧写入口先共享接纳、版本和故障边界。
   在完整初始化材料未具备前，可以验证内部组件，但新运行入口保持关闭。
4. 按消费者迁移角色/成长/资源及其余领域，逐项给出事务、随机性、结果、历史、增长预算
   和存档覆盖；不能只替换 Servlet 的 loader 而遗漏 JDBC 内的规则 JOIN。
5. 汇总完整文件、直接恢复、结束保存/清理/修复、权限、容量和故障恢复验收。
6. 跨领域候选通过后，分别执行规则发布、数据库迁移/授权、应用部署和默认采用检查点。

这是依赖顺序，不要求每层所有未来能力先做完，也不授权创建空表/空接口。任务拆分应使每个
采用结果可以独立验证；新旧混合阶段要明确仍依赖旧库的路径，不能宣称整个应用已完成拆分。

## 未完成与暂缓边界

以下边界仍阻止相应能力，不因记录设计而关闭：

- 完整初始/当前角色、装备/冒险、战斗/效果、法术、怪物/魔法物品及各历史类型的准确字段、
  引用、执行/恢复和独立覆盖尚须完成；语言或 NOTE 分区不能构成可运行的完整文件。
- 共同守卫的全部入口、真实 SQL/触发器、完整删除图、权限和故障连接隔离尚需逐项采用。
- 候选、最终档、长期技术事实、规则加载及解析/编码的物理容量和长期增长须有实际证据；
  设计预算和历史测试记录不能代替验收。
- 首次新建 v2 战役、角色作者输入白名单、编辑器及动态角色接纳暂缓；不以空战役绕过。
- 兼容区间、旧战役升级、冒险/机制拓展包、未知效果人工放行及多实例接管另行设计。
- 存档/规则/应用的独立制品保管、数据库回退后的身份连续性和实际恢复工具仍须落实。

## 验证与发布

每个实现切片使用相关定向测试，覆盖正常、边界、坏规则、跨运行串用、过期版本、幂等、
事务失败和禁止部分写入。来源、运行镜像与文件必须有独立字段/字节期望；仅自洽往返不足。
真实约束、权限、锁与连接语义需要隔离 MySQL 验收。全量测试、打包/WAR 审计及发布检查点
按[测试指南](../../testing.md)与[完整规则门](../../rules/srd-5.1-complete.md)执行。

保护 legacy v1 的行为、身份、摘要、算法与格式 1；已应用迁移只能追加。发现确需保留的
真实 DRAFT 数据时先明确迁移要求，不默认丢弃或引入全面兼容。旧类名、旧 DRAFT profile
和旧 codec 形状本身不构成永久承诺。

设计批准不等于数据库安装、发布或部署批准。规则安装、迁移、授权、备份/恢复、WAR
部署、发布状态和默认切换是各自检查点；普通应用启动不自动执行其中任何写操作。
