# v2 玩家步骤与自动保存

状态：玩家计步是业务目标；SQLite 命令持久化、检查点屏障和完整文件保存均未实现。
现有 MySQL INTERNAL 的局部时间/休息、战斗与恢复不等于本页能力已采用。
本文中的玩家是游戏参与者，不是网络账号，操作入口仍由单一 DM 控制。

## 步骤与模式

| 场景 | 一步的含义 | 不计步的操作 |
|---|---|---|
| 非战斗 | 一名玩家在一轮中的全部操作，多个 PC 合计一步 | 单次检定、消息或字段修改 |
| 战斗 | 一个 PC 的完整角色回合；同玩家多个 PC 分别计步 | NPC 回合、回合外反应、打开回合及模式交接 |

DM 显式确认完成，服务端检查准确步骤/回合身份、完整目标、版本、事件尾和领域完成条件。
空操作的正常确认、放弃剩余操作均计一步；放弃不撤销此前已提交状态、消耗或历史。
重复请求不重复计步，不同请求指向同一已完成步骤也不能创建第二次完成。

非战斗使用稳定玩家键、固定顺序及玩家到 PC 的映射；每个 PC 恰属一名玩家，每名玩家至少
有一个 PC。当前固定名单阶段不支持动态增删、重排或把映射 PC 改成 NPC；角色归档、死亡
或无法行动不自动移除玩家。全部 PC 不可行动时可以确认空步，但不授予角色行动资格。

模式有唯一权威来源，不能用“没有遭遇行”推导非战斗。进入战斗挂起当前未完成的非战斗
步骤；退出后恢复同一步，不补计步、不清零轮次。进入、打开回合、完成回合、离开战斗都
是独立受保护命令，回合规划和安全交接由战斗领域证明，不能复用 v1 最小遭遇状态冒充能力。

完成确认本身不自动结算骰子、选择、效果或资源；必须在完成前处理的义务由各自命令先
完成。合法跨步骤持续状态继续保留。缺少任一领域的完成判据就拒绝确认，不靠前端布尔放行。
迟到的上一模式/步骤请求在随机性前拒绝，模式往返不能恢复旧请求资格。

攻击、移动、施法和反应的完成义务统一通过[动作继续协议](action-continuation-protocol.md)
判定。未终结动作流、未决定选择或尚待继续的已关闭窗口均阻止步骤/回合完成；反应子帧
和继续命令不独立计步。合法跨回合的 Ready 准备、持续施法或效果仍由其领域持有，不因
具有未来触发义务就一直占用当前动作流；到期与 CLOSING 所需结算另按登记的完成条件处理。

持续效果按[持续效果协议](ongoing-effect-protocol.md)登记本次边界的到期、周期触发、贡献
变化和结束义务。压制中的实例仍按各自计时合同参与完整边界检查；不能只扫描当前提供
贡献的效果。当前必需转换/回调未结清时保持 CLOSING，之后才计步；未来尚未到期的合法
存续状态继续保存，不因回合完成自动解除或重新施加。

## 命令持久化与检查点水位

每个成功新业务命令都在同一 SQLite 业务事务中持久提交完整状态、历史和接受结果，并
推进本地 `commitRevision`。步骤完成、NPC 操作、反应、消息、模式交接及动作继续只要
形成业务提交，都参与 revision；玩家计步不是唯一耐久性触发。精确重放、GET 和保存
控制事务不推进 revision。一个玩家步骤包含多个已提交命令，不持事务等待整步完成。

本地 `checkpointRevision` 记录最近成功接受的完整检查点所覆盖的 revision，必须满足
`0 <= checkpointRevision <= commitRevision`。首个完整检查点接受前不开放游戏写入；
新建和文件恢复都遵循这一门槛。同版本地恢复保留已证实水位，文件独立恢复重新建立。
revision、水位、epoch、本地 CAS 和保存收据不进入可移植文件；业务轮次、当前玩家、
步骤/回合、模式、时间及未完成过程则完整保存。

应用分别限定未检查点 revision 距离和增长量，任一先达到有界阈值，就在该业务提交后、
下一新游戏命令接纳前建立自动保存屏障。revision 距离为
`commitRevision - checkpointRevision`；增长量是自最近检查点后，每个成功命令造成的
完整规范文件字节数正增量之和，逐次精确计量、回退不冲减，重复请求不重复累计。它不是
SQLite 页数、行数或 UI 估算；更新同业务提交一起持久化，检查点接受才归零。同版本地
恢复保留该计量，独立文件恢复重新建立。任一运算溢出在 RNG/写入前拒绝，测量方法和
有限参数须以全域工作集与故障实测验收。随机分支先按有限最大编码增长预检，成功后核
实际字节并更新计量，不能消费 RNG 后才发现计量或完整保存容量不成立。

这里不规定固定步数、档案份数或字节预算。每个本地已提交命令的精确恢复依赖运行库
持久提交，可移植检查点周期不改变该事实。

屏障对 NPC、反应、继续命令、消息、模式交接和下一回合同样生效。到阈值时可能正处于
OPEN 窗口、CLOSING、未决选择或移动中途；保存该准确前缀，不替玩家结算来凑完整步骤。
保存不依赖浏览器补请求，旧命令重放、GET、启动或下载不触发新保存。服务端在真实新
提交的后继协调中发起检查点；失败仍保留原业务成功事实。

## 保存屏障与模式交接

保存使用[保存与恢复](save-and-recovery.md)的意图、同卷临时文件、独立读验、不可变
generation 发布及运行库收据协议。文件 I/O 不跨数据库事务，源 revision 在短写门内
固定；不另建数据库档案字节晋升流程。generation 保留及清理按保存合同处理，计步模块
不复制轮换规则。

| 触发/转换 | 前置及 R/W | 事务与成功点 | 可重入及失败去向 |
|---|---|---|---|
| 新建/文件恢复首个检查点 | PREPARING，R 完整新运行源，W 原保存意图/收据 | 完整发布并明确接受收据后才可 ACTIVE | 原意图查证/重试；失败保留准备源，不开放游戏写 |
| 业务提交达到任一阈值 | 新命令已明确提交，R revision/水位/精确累计增长，W 自动保存意图 | 接纳门先建立 AUTOSAVE 屏障再保存，不回滚已成功业务 | 只重试原保存意图；失败保持屏障，未知按 UNKNOWN 查证 |
| 自动检查点接受 | R 准确正式字节、固定源和原意图，W 收据/水位 | 接受事务明确成功且其他阻断已消除后释放屏障 | 重放原事实不再保存；失败继续屏障，不提供忽略保存继续入口 |
| 普通手动保存 | ACTIVE，排空命令并暂时拒绝新游戏写，R 固定源，W 保存控制 | 同一发布协议明确接受后回 ACTIVE；不更改步骤或业务 revision | 已决失败可取消并恢复原运行；发布/提交未知保持阻断，不另起保存覆盖 |
| 保存中显式 END | 先确定原保存结果，排空命令，R 最新完整源，W END 意图/seal | 最终收据和 seal 明确接受后为 SEALED | 封存前已决失败可重试或取消 END；原 AUTOSAVE 原因仍在时保持屏障，封存后仅清理/受控修复 |
| 步骤/回合完成及模式交接 | ACTIVE、当前 epoch/步骤身份及完整领域完成条件，R/W 业务和公共历史 | 独立命令提交完成事实/revision，再按水位判断屏障 | 相同完成不重复计步；旧模式意图拒绝，失败不提前计步或推进模式 |

界面分别反馈“命令已完成”和“检查点尚未完成”。保存失败不要求重做原命令；自动保存
失败不能引导换请求键重做步骤或绕过屏障。重试绑定准确运行、epoch、保存意图、源
revision 与 fileKey/generation；旧页面不能自动跟随当前候选。已接受检查点的不可变
结果与对应文件目前是否仍存在分开查询。

技术 END 保存最新中途状态，不替玩家完成步骤、PASS、关闭窗口、结算时间或清理效果。
自动保存屏障和正常手动保存的短写门不成为长期动作阶段或玩家模式，由
[运行生命周期](runtime-and-transactions.md)控制接纳。重启、未知和完整性阻断优先于
计步策略，同版残留经完整查证及显式恢复后才取得新 epoch 的游戏资格。

## 采用与验证

先证明每条真实写路径使用共同接纳、单写业务事务和 revision，检查点覆盖全部规则绑定、
业务、历史及因果引用。验证包括 revision/增长任一阈值前后一条命令、单步内多次提交、
大小回退不冲减计量、计量溢出、NPC/反应/消息触发、
OPEN/CLOSED 窗口和 CLOSING 保存、重复完成、模式往返、并发保存与 END、首个检查点
失败、发布后收据未知和重启水位查证。固定阈值的正常路径不能替代这些边界。

SQLite 持久提交、文件发布和恢复的真实平台故障验证，各领域完成判据、完整文件
reader/writer 及 Host 接纳都完成后才开放。新建编辑器和名单取得仍受
[产品暂缓范围](../../product.md)约束，本页不从设计产生可执行入口。
