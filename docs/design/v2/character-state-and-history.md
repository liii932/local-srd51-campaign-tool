# v2 角色状态与历史

状态：以下为当前选择的完整战役状态与历史合同；私有运行库、完整文件及统一战役初始化
尚未实现。适用范围见 [v2 设计导航](README.md)，现有内部切片不是本合同的完整采用。

## 战役工作集和四类根

| 目标责任 | 内容 | 生命周期 |
|---|---|---|
| `runtime_campaign_workset` | 本次 run/snapshot 下的战役根 | 完整初始化建立，可靠结束后清理 |
| `runtime_character_identity` | 战役内稳定角色身份 | 普通归档/离场保留，防止历史主体悬空 |
| `runtime_character_initial` | 加入战役时的不可变初始卡头及其领域内容 | 不随当前状态更新 |
| `runtime_character_current` | 当前名字、PC/NPC、记录状态、版本及各领域当前状态 | 由获准业务命令修改 |

上述为私有运行库内的目标责任，不是已应用 SQL。一个战役的全部角色共用本次 run/snapshot
和根事件尾；替换当前 INTERNAL 的单角色 run 与跨多个 prepared identity 拼接战斗的模型，
不能只替换 JDBC 驱动。一个角色恰有一个初始头和当前根；不建立
没有战役的角色根。初始卡可以是任意合法加入等级，不等于一级创建快照，也不等于本次
导入时的当前卡。恢复不得重新套模板、升级、掷骰或从初始值推算缺失当前值。

## 身份与引用

- `campaign_key` 和 `(campaign_key, character_key)` 是可移植业务身份，恢复原样保留。
- `run_id`、`snapshot_id` 和本地战役/角色行 ID 在独立导入时重新生成，不进入产品文件。
- 新根的 UUID 使用严格 UUIDv4 网络序 16 字节；本地数值 ID 使用 Java `long` 可精确表示
  的正有符号 BIGINT。旧 v1 的物理列不因这个目标改变。
- 同一角色、战役、run、snapshot 的复合归属贯通到所有领域子行；规则引用使用该行同一
  `snapshot_id` 加领域键。只查全库 `character_key` 不能选择活动对象。
- 名称允许重复，不参与身份匹配；名称为 NFC、1—80 Unicode 码点并拒绝控制字符和空白值。
  恢复/存储读回拒绝不规范值，不能悄悄改写历史名称。
- 本地 `row_version` 用于聚合并发，独立导入从 0 开始；不从文件恢复，不因只读或重放推进。

PC/NPC 表示角色类型；ACTIVE/ARCHIVED 表示记录管理状态。它们不表示账号权限、生命状态、
轮到谁或当前运行是否可执行。业务状态、初始状态和技术生命周期各自只有一个权威来源。

## 完整业务历史

所有历史类型共享战役内一份根事件序号空间，当前状态来源引用这份根。目标责任分别为
事件尾、公共事件根和各类型历史正文；不并存可独立漂移的 `stateEvents`/`recentEvents` 根。

稳定历史身份是 `(campaign_key, event_sequence)`。序号和事件尾是精确有符号 long，不能
经过浮点或 JavaScript Number 丢失精度。新业务按尾分配下一序号，并与状态、类型化历史、
版本、计费和幂等结果一起提交；失败不推进。恢复保留原序号和尾，不按插入次序重编号。

保存覆盖全部已记录业务历史，最近若干条只用于 UI。恢复不补造未记录历史，不把序号空洞
填成 NOTE；尾不小于现存序号，保存时必须独立比较全体已存根及正文，不能借允许空洞删历史。
不执行历史来重建当前状态，也不恢复旧命令的幂等执行权利。

独立 DM 消息 `NOTE` 是首个完整设计的历史类型：一根一正文，无角色主体、骰子或效果。
检定附带消息属于该检定根，不能改装成独立 NOTE；未知历史类型不能降为通用文本。
类型化来源还须检查事件类型、主体和领域资格，外键存在本身不足以证明来源正确。

归档或离场的角色、已消耗物品和已关闭过程仍须保留历史所需引用。完整删除只属于可靠
结束的工作集清理，不能在普通业务中删去身份再用名称或空引用替代。

## 新建与文件恢复的公共初始化输入

新建与文件恢复都产生封闭 `InitializationPlan`，由应用完整验证后才分配可执行根。计划包含：
准确规则绑定/完整最终快照与链、战役稳定身份和名称、固定玩家名单/PC 映射、角色全部初始
及当前状态、所选规则要求的场景/空间和统一业务时钟、全部历史及事件尾、所有动作/效果
待办、字段覆盖清单和已验证存储闭包。不是只提交一个角色授予计划或空分区集合。

- 首次新建由受支持的角色创建输入和明确初始场景材料构成；身份由服务端生成，角色初始
  与当前从同一已验证事实建立。需要随机创建时，随机决定在受保护初始化内恰发生一次，
  结果/初始事实/收据同事务保存；准备预览不预先掷骰。新建允许无历史的明确起点
  eventTail=0，之后新事件连续分配；不能伪造既往升级/冒险历史来解释初始等级。
- 从文件恢复保留业务身份、初始/当前差异、全部已记录历史和准确事件尾；新建本地
  run/snapshot/CAS/安全代次。文件校验过程只验证既有骰点和计算，不调用业务消费者。
- 初始化事务保存整个闭包，实际读回后核验。明确提交且首份完整检查点可靠保存后才
  开放新游戏写入；失败留下可诊断的准备/残留，不发布部分角色或半个战役。

输入 UI、角色编辑器和完整创建适配器仍未实现；本节确定其必须提供的数据与失败边界，
不把公共新建合同延后，也不以空战役绕过缺少的具体消费者。当前完整基础仍为 DRAFT。

## 状态所有权和完整历史的接合

[完整文件分区表](save-and-recovery.md#完整文件外壳与分区)是所有状态 owner 的保存/恢复
责任清单。角色 HP、装备、资源、时钟、场景、flow 和效果不得各自复制可写当前值；场景
结算产生的角色子事实与根事件、成本、选择、骰子、效果和结果同事务提交。
业务时钟只有一个权威，保留精确秒及领域原单位/边界；角色休息与场景推进必须协调全部
受影响 owner，不能把多个单角色时钟的局部恢复相加当作完整战役恢复。

当前内部角色/战斗历史的 before/after、原骰和因果输入属于已记录业务事实，全部进入
文件。目标历史可以类型化设计，不能为了压缩体积悄悄丢掉当前已有审计字段。只在只读
验证器中用保存的结果验算状态邻接；实际恢复直接写已验证状态，不通过历史事件驱动执行。

幂等 HTTP operation 与业务 action/event 身份分开。现有代码以 operation UUID 兼作因果
键的地方必须建立准确映射并保留业务引用；从文件恢复不带旧请求收据，但不能丢掉因此
被引用的动作、消费、掉落或效果来源。恢复本地残留保留同 run 收据和原结果，新安全代次
使旧页面失效；查询旧接受结果不授予再次执行能力。

## 采用前必须补齐的内容

公共字段类别与 owner 按上述合同固定；列级映射、类型化 codec、跨域初始化者、独立
向量及运行存储实现仍需逐项交付。目录存在、
根表存在或数组为空，都不能证明领域已覆盖。
