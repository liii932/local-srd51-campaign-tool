# v2 规则存储与版本

当前选择是每次打开战役建立独占的私有 SQLite 工作库，活动期间由它统一拥有准确规则、
状态、全历史和本地控制。显式 `DND_STORAGE_ROOT` 已采用这一有限应用路线；未配置时仍
使用原 MySQL 简化模式。完整 SRD、自定义包安装及默认切换分别有自己的门，不由换存储完成。
当前字段/入口与差异见[领域接合表](domain-integration.md)，使用方法见
[运行合同](../../storage-vitality-loop.md)。本页不记录某次测试、安装或部署结果。

## 选型与单一权威

| 材料 | 当前责任 |
|---|---|
| 应用内四个准确 schema-2 原包 | 随版本交付，生产 reader 验证原始 ZIP 后 compose；建立本版有限规则支持边界 |
| 每次打开的私有 SQLite | 完整固定规则/链、初始/当前事实、全部历史、pending、根因果和本地接受/保存控制的唯一活动权威 |
| 完整逻辑 JSON | 一个已提交状态的不可变便携保存点，携准确 material/完整链和全业务图；不会随活动运行变化 |
| JVM/页面/查询投影 | 由已验证工作库重建，不能补造缺失状态或成为第二写入权威 |
| 原来源与运行 MySQL | 保留各自现行迁移、安装/接受、独立账号和真实资料职责，不参加当前 SQLite 业务事务 |

选择 SQLite 是为了单 DM、一个活动战役的共同事务和可封闭运行目录；不使用每战役 MySQL
schema、跨库 `ATTACH` 或 JSON 文件直接承担活动事务。原 MySQL SQL/触发器/`FOR UPDATE`
不能机械搬入该模型。Java/Tomcat、loopback 和主机安全边界保持。

当前数据流为：

```text
rule-packages/srd51-runtime 作者 JSON
  → 确定性四个 ZIP（WAR 内 storage/rules）
  → ProductionRuleArtifact.read → ProductionSchema2Projection.compose
  → 新私有 SQLite：固定 material/完整链 + 全领域聚合/关系投影 + 根历史/本地收据
  → 初始、手动、最终完整 JSON；P0—P3 接受后成为保存点
```

未来开放任意自定义包时仍须设计准确原包保管、本地接受、依赖/兼容、机制支持与发布资格，
来源 MySQL 可以承担该独立维护责任。该未来链路不是当前四包新建、文件打开或恢复的先决条件。
现有来源 reader/installer 继续按原合同逐列核验，不能借“索引可重建”省略它们的检查。

## 准确材料和文件中的规则

当前准确顺序是 `srd51_runtime@1`、`srd51_characters@1`、`srd51_magic@1`、
`dm_runtime_house_rules@1`；直接依赖及有限范围见[作者指南](../../../rule-packages/srd51-runtime/package-guide.md)。
它们形成一个有限应用 profile，不是完整 SRD `RELEASED`，不使用完整规则族的 DRAFT 身份。
未知、重复、缺依赖、坏原包、类型/引用、组合或不支持机制失败关闭。

`CampaignDomainData.Material` 保存准确成员、最终规则、entries 和全部字段链。工作库与
完整文件都保留这些材料；`Material.restore` 将四个完整字段集合逐项精确比对本版内置
投影。该投影已经生产 reader/compose 验证并固定 composition、final-rules、chain 三种
指纹，恢复复用它而不逐次重新组合或计算摘要。
不能只保存“规则目录名称+最终数字”，也不能依靠输入自报已接受或相同最终规则替换原组合。

原 ZIP、模组逻辑、组合配置、最终规则和完整链五类摘要各有职责，沿用
[生产制品合同](../../rules/schema-2-rule-artifacts.md)的独立域；物理计划、HTTP 收据与 WAR
摘要不进入规则身份。文件携 frozen 规则不授予任意作者包执行权：应用仍只接受其明确支持
的准确内容/机制。普通命令、保存、打开及同版残留恢复均不要求外部来源 MySQL 在线。

## 应用拥有的结构与聚合

结构唯一源是应用打包的 `storage/campaign-schema.json`：表、列、类型、主外键、索引、
有限约束、静态 seed 与依赖均由应用声明，受限编译器产生 SQLite DDL。模组与战役文件
不能提供表名、SQL、表达式、脚本、驱动、类名或物理路径。新机制须同步声明、消费者、
验证和完整文件；不以占位空表取得资格。严格格式与计划见[结构合同](storage-schema-and-planning.md)。

当前复杂状态采用**严格 typed TEXT 聚合 + 独立核验的关系投影**。闭合 record/enum、
完整必填字段与类型标识由代码登记，未知/缺失字段、错误类型、非规范数值/映射和坏文本拒绝。
这不是自由 JSON 属性袋，也不要求把每个领域叶值拆回 MySQL 子表形状。

角色聚合拥有当前 HP、成长、生命骰/资源、装备、法术书、休息及其完整历史；场景/战斗
聚合拥有先攻、动作树/反应、效果、区域、怪物与完整场景历史。相应资源/装备/法术书/
动作帧/效果/怪物关系表是同事务投影，不是第二份可独立修改的余额或状态。读取逐行核对
正文与投影；任何不符拒绝，不在恢复时重建索引掩盖损坏。具体 owner 见[数据映射](storage-data-map-and-rollout.md)。

规则组合图与应用存储依赖图独立。当前 profile 显式映射存储根，`StoragePlan` 取依赖闭包，
纳入后续全部合法写入、历史与 pending 所需结构；即使现在无角色、法术或效果实例也不能裁剪。
拓扑排序不改变准确规则顺序。未知根、缺依赖、冲突或未处理循环在分配目录/RNG 前拒绝。

## 初始化、身份和离线恢复

只在新分配的空私有库中，一个事务建立 DDL/索引、静态 seed、完整规则/链、业务/历史和
本地控制，提交后从健康连接独立读回。首份完整检查点 P0—P3 接受前不开游戏写入。
同版残留只核对原模型/计划和真实结构，不执行补表、ALTER、重新 seed 或历史重放。
初始化未知先独占查证，不换目录、规则或操作标识重做。

物理 `core_control.run_id`、epoch、HTTP 请求/保存收据属于新本地运行，不进入便携文件。
schema-2 初始计划/状态/历史中的 prepared `Identity`（其字段仍名 runId/snapshotId）是保留
业务关系的稳定标识，随文件保存，不能当作旧连接或 HTTP 执行资格；打开不重写这些历史键。
角色事件 version 也是保留历史的邻接事实，本地 Host revision/epoch 则重新建立。

每个命令通过实例/目录独占门和一个 `BEGIN IMMEDIATE`，业务后果、根/子历史、版本与
接受收据共同提交。没有独立 C0 接纳事务或另写 NOT_COMMITTED 裁定；未知提交/回滚禁止
新写，显式恢复独占真实库、完整事实/全部收据后建立新 epoch。没有持久接受事实的请求
不自动重试，不从日志重播命令。具体边界见[运行与事务](runtime-and-transactions.md)。

## 版本、保管与采用

| 标识 | 用途 |
|---|---|
| 模组完整身份/准确字符串版本 | 原内容、依赖、覆盖及当前支持范围，不比较“最新版本” |
| canonical/组合算法/规则摘要 | 准确规则与解释过程，不是物理 schema 版本 |
| applicationModel/文件 kind/formatVersion | 当前受支持业务文件协议，不按数字大小猜 reader |
| storageModel/精确模块清单/plan digest | 只绑定本地结构/初始化和同版残留核验，不进便携文件 |
| 本地 run/epoch/revision/收据 | 当前实例执行、并发、查证及保存控制，不赋予文件旧请求权限 |

原型只支持当前应用声明的模型。未来可协调替换模型/编码/目录，但不能重新解释仍保留
事实、静默转换旧数据或改 MySQL 已应用 checksum。保留库用前向迁移，重建/重置与真实
数据处置须独立授权。现有 MySQL 和来源账号/安装账本继续独立保管。

WAR 必须含四个受控内置 ZIP、声明、编译/严格 codec/领域服务及 SQLite JDBC；其他作者
目录、来源维护 SQL、离线写入类、真实库/journal/存档、凭据与日志仍排除。实际部署、迁移、
接受、发布和默认切换是不同检查点。当前 JDBC/文件系统的崩溃、锁、刷盘、低磁盘和
清理证据按[测试指南](../../testing.md)取得；正常往返不证明断电耐久或完整 SRD。
