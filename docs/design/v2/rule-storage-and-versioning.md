# v2 规则存储与版本

本文规定[四层设计](module-layering.md)的规则绑定、活动存储与恢复。每次新建或从文件
打开战役建立一个独占的私有 SQLite 工作库，规则制品和准确接受由[本机规则库](local-rule-library.md)
保管。当前 SQLite 路线接合本机原包、独立接受与有限机制组合。实际入口和覆盖见
[领域接合表](domain-integration.md)。

## 选型与单一权威

| 材料 | 目标职责 |
|---|---|
| 本机规则库 | 准确原包、导入绑定和本机 DM 接受的权威，为准备战役提供只读材料 |
| 每个物理运行的私有 SQLite | 固定规则和链、初始/当前事实、全部历史、未决事项、根因果和本次命令/保存收据的唯一活动权威 |
| 完整逻辑文件 | 一个已提交状态的不可变便携保存点，携准确冻结材料、完整覆盖链和全业务图 |
| JVM、页面和查询投影 | 由已验证的事实重建，受相应权限限制 |

单 DM 任一时刻使用一个活动战役，可以保管、保存和切换多个战役。每个战役的身份、准确规则、
业务事实和未决事项分别保存，便携文件和运行私有目录分别定位。可共享的是不可变的原包及只读
规则材料，各战役独立绑定准确版本和来源。目标运行及规则保管均在本机，工作库和规则库各自
维护自己的事务和引用。

当前数据流如下。

```text
作者原始 ZIP → 本机规则库导入与明确接受
  → 开始前复核准确成员，验证组合和应用支持范围
  → 新私有 SQLite 保存冻结材料、完整业务图、历史及本次控制
  → 已提交状态的完整保存点
```

## 准确规则绑定与冻结材料

冻结材料包含有序准确成员和双摘要、作者与组合协议、完整最终类型化规则及条目、完整字段覆盖链。
每个规则绑定有组合配置、最终规则和覆盖链三个独立指纹，并在工作库和完整文件中保存应用定义的
准确机制解释协议标识。命令按该标识解释冻结规则及权威事实。身份、来源、链终值和全部引用须与
完整材料一致。规则库与用户预设的后续变化不改变已绑定战役。物理计划、目录名、数据库 ID、HTTP
收据及 WAR 摘要独立于规则身份。五类摘要的职责见[模组接口](module-interface-baseline.md#五类摘要规则制品与战役文件)。

应用核验每个被消费的机制、模式、参数、引用及其历史和恢复责任，按所选组合的完整能力闭包
取得资格。通用组合的核验针对该战役的准确材料，资格取决于本机接受、完整组合及当前应用的
领域支持。材料可核验和指纹相符只是该检查的一部分。

完整文件保存准确绑定、冻结材料、全业务图、原骰和未决事项。打开后直接恢复已保存的事实，
保留原规则、来源和历史。组合名称、可编辑预设、最终数值或文件自报接受均不能替换准确材料。

## 完整文件打开前的规则核验

新建和正常打开文件都从本机规则库取得准确原包和本机接受。打开时使用文件所绑定的原有序
版本，由已验证的原包重新组合出校验候选。逐项核对文件内的准确成员、完整规则与条目、完整
字段链及三类组合指纹，核对所绑定的机制解释协议符合应用的本版支持合同，再验证业务与历史
并直接装载已保存的事实。规则组合只用于材料核验，不重做游戏命令或初始化已保存的角色。

换到新机器时，先取得并在该机导入、明确接受文件需要的准确原包，再打开文件。接受记录随
规则库保管。文件和组合 ZIP 可移交材料，但不会授予本机接受或执行资格。缺包、未接受、
错误组合或当前版本不支持时拒绝打开，保留原文件。规则库故障对已绑定工作库的影响按
[残留恢复](#初始化身份和离线恢复)处理。

## 应用拥有的结构与聚合

物理结构和类型由应用维护。模组与战役文件不得提供表名、SQL、表达式、脚本、驱动、类名或物理路径。
角色、空间、战斗、效果等领域各有自己的权威事实和写入者。关系投影如用于查询须与权威正文同事务
更新，恢复时核对投影与正文。具体事实所有者见[状态与历史](character-state-and-history.md)。

规则依赖图与应用存储依赖图分开核验。应用预备全部受支持机制的未来写入、历史与未决事项所需结构。
当前没有角色、法术或效果实例仍须覆盖后续合法写入。存储装配顺序不改变规则加载顺序，缺失依赖、
未知结构或不支持能力在分配运行和消费随机性前拒绝。当前 JSON 结构源、严格聚合、核验投影和计划见
[结构合同](storage-schema-and-planning.md)及[数据映射](storage-data-map-and-rollout.md)。

## 初始化、身份和离线恢复

新建或文件打开时，在新分配的空私有库中一次提交结构、初始规则与完整链、业务和历史、本地控制。
提交后独立读回并按[运行与事务](runtime-and-transactions.md)完成首份检查点，再开放游戏写入。
同版残留核验原有结构和计划，缺损保留阻断。初始化未知先独占查证原结果，保留原目录、规则和操作标识。

运行标识、epoch、HTTP 请求与保存收据属于本地执行控制。文件打开重新建立这些身份和权限，
保留战役、角色、规则绑定及根子历史的稳定业务键。已接受骰点、消耗、已完成后果及未决事项直接恢复，
待继续动作保持原进度。

普通运行、保存及同版残留恢复使用工作库的完整冻结材料。残留恢复核验原准确规则绑定、机制解释协议、
结构和全部事实、历史、未决事项与本地收据，经显式恢复获得新 epoch。规则库缺包或离线不更改已经
固定的业务解释。材料缺损、解释协议不匹配或提交未知按[运行与事务](runtime-and-transactions.md)保持阻断。

## 版本、保管与采用

| 标识 | 用途 |
|---|---|
| 模组完整身份与准确字符串版本 | 准确原内容、依赖、覆盖及支持范围 |
| 作者、canonical 与组合协议 | 解析、组合及规范摘要校验 |
| 机制解释协议 | 应用在该战役中执行冻结规则及验算历史所使用的准确语义 |
| 应用与文件协议 | 当前受支持的业务状态与便携文件 |
| 本地结构模型与计划摘要 | 本地初始化和同版残留核验 |
| 本地 run、epoch、revision、收据 | 当前实例执行、并发、查证及保存控制 |

原型只支持当前应用声明的模型。旧格式和未知协议在写入前明确拒绝。真实数据保管、应用
发布与运行采用按[采用边界](adoption-boundaries.md)及[数据库合同](../../database.md)
分别处理。具体物理结构、文件协议编号及受支持容量随实际采用和验证确定。

## 当前有限实现

显式 `DND_STORAGE_ROOT` 启用私有 SQLite。WAR 提供标准和检定变体所需的五份原包作为导入候选。
DM 明确选择本机已接受的有序准确成员。`ProductionRuleArtifact` 和 `ProductionSchema2Projection`
读取与组合，`CampaignRuleSupport` 校验现有建卡模板和执行机制的闭包。
工作库与文件使用 `CampaignDomainData.Material(interpretation,binding,rules,entries,chains)`。
`Material.restore` 从冻结行重建投影、核对绑定及支持合同，并以完整不可变材料为键共享至多两份
已核验上下文。[作者指南](../../../rule-packages/srd51-runtime/package-guide.md)、[运行合同](../../storage-vitality-loop.md)

当前应用模型为 `campaign-spaces-3`，本地存储模型为 `sqlite-campaign-3`。完整文件使用
`RULE_BOUND_CAMPAIGN` format 3，规则绑定、角色和全部空间事实位于完整 `domains` 中，`campaign.eventTail`
核对该聚合内的根历史。`Schema2PreparationIdentity` 的 `runId/snapshotId` 字段属于稳定业务引用。
物理 `core_control.run_id`、Host epoch 和本地收据属于本次运行。应用 JSON 声明结构与投影，
用 `BEGIN IMMEDIATE` 共同提交，并按 P0—P3 发布完整文件。
未配置显式 SQLite 时，现行原 MySQL 简化模式继续沿其自己的迁移、JNDI、来源权限和数据合同。
