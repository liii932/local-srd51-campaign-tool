# v2 规则存储与版本

状态：目标选择每次打开战役时建立独占的私有 SQLite 运行空间，保留独立 MySQL 规则来源与接受账本。
当前代码仍是 MySQL 运行库；SQLite、完整文件与全生命周期尚未采用或验证。方案可随需求与证据修订。
本文件按 [v2 设计导航](README.md)区分设计选择、实现与发布；模组组合、身份与摘要的
公共合同统一见[模组接口基线](module-interface-baseline.md)。
作者 schema 2 的具体输入、组合步骤、最终字段与来源链核对见
[最小组合链路验证](schema-2-composition-validation.md)；生产原包与摘要采用[制品合同](../../rules/schema-2-rule-artifacts.md)，
维护操作采用[安装与接受](../../rules/schema-2-installation-and-acceptance.md)。有限投影和维护事实
不代替完整基础验证、机制接入或运行快照的实际读回验收。

## 选型与单一权威

| 候选 | 与完整文件生命周期的关系 | 选择 |
|---|---|---|
| 多战役共享 MySQL 运行表 | 事务与现有实现接近，但每次结束都须证明全域删除图、入向引用与其他战役隔离；残留、收据及配额易成为全局耦合 | 保留为当前实现，不作为新目标 |
| 每次打开一个私有 SQLite 数据库 | 完整规则、业务和历史在本地同一事务边界；封闭后可按整个运行空间清理，适合单 DM、一个活动战役 | 选用；须通过真实 JDBC 与文件故障验证 |
| 每次打开创建 MySQL schema | 可物理隔离，仍依赖外部服务、建库权限和数据库级清理；应用账号职责更复杂 | 不选 |
| JSON 直接承担活动写入 | 文件交付简单，但需自行实现跨状态、历史、幂等和 pending 的原子修改及崩溃恢复 | JSON 只作为业务文件协议 |

SQLite 的选择由本机单 DM、完整文件交付与运行空间可封闭的需求决定，不由复用现有仓储决定。
它不改变 Java/Tomcat Web 入口；也不声称现有 MySQL SQL、触发器和事务守卫能直接复用。

目标数据流如下：

```text
分域 JSON 作者源 → 严格校验与受控安装
  → MySQL 来源库：准确原始规则 ZIP、安装/接受事实、来源迁移账本
  → 开始/文件恢复时读取准确有序组合、复核接受、重新组合；结束并关闭来源连接
  → 应用私有运行目录中的 SQLite：完整最终规则 + 完整覆盖链 + 业务状态 + 全部业务历史
  → 完整逻辑 JSON 战役文件；可靠发布并验证后，才可清理本次运行空间
```

各层职责只有一个写入所有者：

- 作者 JSON 是可审查的规则内容输入；已安装的准确原包与不可变安装/接受事实决定本机可用来源，
  运行请求不修改或自动接受它们。来源类型化镜像在目标中降为可重建索引，不再要求每个新领域
  复制一套来源表；索引不能提供原包缺失的规则、接受资格或另一份可编辑权威。
- 打开期间，本次 SQLite 的完整固定规则、业务状态和历史是唯一活动权威。JVM、页面、旧 JSON
  与来源索引均不承担并行写入或故障补值。运行规则镜像不独立编辑，规则切换须结束本次运行。
- 已发布 JSON 是其保存点的可移植业务事实；打开后它不会随命令变化。运行空间负责尚未进入
  可靠文件的最新提交，不能以旧 AUTO 或同名文件覆盖残留。文件发布与运行清理按
  [保存与恢复](save-and-recovery.md)分别证明，数据库 commit 不等于外部文件可靠发布。

规则 ZIP 与战役 JSON 分离。组合恰有一个完整 `base`，可带零到多个 `extension` / `compatibility`；
依赖、联合兼容和顺序按公共基线核验。战役文件不携带规则正文或完整规则值覆盖链。
准确组合规则包可作为清单和成员原包的分发容器，不增加第三份规则权威或接受入口。

## 应用拥有的结构与机制闭包

运行状态仍使用**领域关系表和类型化列**。规则 JSON 描述固定类型的规则内容，不描述任意
表名、列、类型、SQL、表达式、触发器或可执行脚本。接受模组不授予建表能力。

应用使用受版本控制的封闭 JSON 模块清单，登记模块 ID、准确协议、有限依赖及随应用交付的
固定 SQL 资源引用，并绑定读写/校验实现。该清单是应用实现元数据，不是模组作者输入或可移植规则身份。
DDL、约束、索引、创建顺序、校验和文件投影均由应用负责；不能把它扩成通用 JSON-to-DDL 框架。
规则或文件只能要求应用已知的能力，不能指定物理对象或从输入路径加载 SQL。

建表范围由应用计算完整依赖闭包，根集合同时包括：

1. 战役身份、规则绑定、事件与历史、版本/幂等、运行状态及保存恢复必需的核心模块；
2. 准确组合的完整规则材料和所需真实机制，包括禁用规则的内容、来源链及引用；
3. 文件必需分区与全部已有业务历史，包括已终结实例仍被引用的事实；
4. 未决动作、窗口、选择、准备材料、持续效果、压制和其他继续义务所需的模块。

在上述根上递归展开应用定义的依赖，固定顺序装配；未知能力、缺依赖、冲突和未处理循环都
失败关闭，不按非空表或当前启用内容猜测。需要相互引用的一组结构应合为经审查的共同模块，
不能借循环跳过创建或验证。文件不得自行省略必需分区来缩小结构。
例如施法的闭包可能包括法术位、装备/健康、动作流、反应、持续效果、专注和时钟；只创建
“法术表”无法保存其真实后果。模块粒度按事务所有者和机制闭包划分，不按每个法术建表。

应用在空私有数据库中装配固定结构，在同一初始化事务中保存组合、完整最终规则快照、
完整覆盖链、初始或恢复业务状态、全部历史和必要本地控制事实。所有规则引用必须约束到
同一快照和准确身份。实际读回并独立验证结构、字段、链、引用、历史与源投影后，初始化
commit 明确成功，并按[保存协议](save-and-recovery.md)完成首份完整
检查点 P0—P3 接受，才发布执行视图。首份检查点缺失、失败或结果未知时保持阻断；只比较
行数或头摘要不算完成。DDL 的事务行为必须经所选驱动验证。
禁止业务运行时按新请求补表、从来源补字段或扩大机制闭包。

## 每次打开的空间与离线边界

新建或从 JSON 打开时，应用在受控根目录分配新的互异 `run_id`、`snapshot_id` UUIDv4 和随机私有
目录，文件中的战役稳定键不能决定目录名或数据库路径。路径、SQL 模块、连接参数和运行身份
不从上传 JSON 取得。目录分配、排他锁和清理须验证真实路径边界；旧浏览器请求不能写入新运行。
应用一次只发布一个活动运行，并同时取得进程与运行目录的独占所有权；SQLite 写锁不代替
工具级的“一个活动战役”判定。初始化失败的目录不具有执行资格，未决提交也不允许换目录重试。

完整残留是崩溃恢复材料。支持当前同版应用在用户显式恢复后，验证数据库、固定规则/链、
完整状态/历史、待办、身份和旧事务已决，再继续该本地运行、保存或结束；不强制只救援 END。
恢复同一残留保留其身份和已接受操作事实，不把它当作新文件导入。独立 JSON 恢复分配新身份，
不复用文件中的技术收据。缺损或未决残留保持隔离，不自动丢弃、回放命令或以旧文件覆盖。
已完成 END 封存的运行只可继续清理或修复保存，继续游戏须从完整文件新开运行。
首份完整检查点尚未接受的残留只可继续初始化/保存协议，不能借残留恢复取得游戏执行资格。

来源库不可达时，已具备完整固定材料且验证通过的活动运行或本地残留可以继续、保存和结束，
执行命令不查询来源库或持有其连接。它不能据此创建新组合、接受新包或从 JSON 重建规则。
文件恢复仍须取得原准确规则包并核验本地接受事实；缺少原包或不能核验接受时可做有界结构
预览，不能激活。完整文件还须同时匹配 `formatVersion=2` 与应用明确支持的准确
`applicationModel`，旧内部数字 2 角色片段不因此成为本协议。两侧没有跨库外键或分布式事务，
来源事务必须在运行初始化前结束并关闭。

运行身份仅用于本地执行与故障判定。当前 MySQL 原型具有永久身份/操作表；目标不因此要求
永久累积所有已封闭运行的全局收据。必要保留范围、文件发布事实与崩溃恢复材料随生命周期
合同验收，不能在仍有未决操作或未可靠保存时回收，也不能把删除真实资料当作设计修订动作。

## SQLite 采用与验证门

此处选型不修改当前 `jdbc/DndToolSE`、`jdbc/DndToolRules` 或环境变量合同。现有运行迁移
V001—V042 与独立来源迁移仍按 MySQL 实现核验；SQL 文件存在不证明目标数据库已应用。
替代运行实现使用独立初始化协议及应用拥有的 SQLite SQL 模块，不复用 MySQL 迁移编号或
改写已应用校验和，不保留仅为旧草稿格式服务的双读/双写。来源索引职责变化同样须协调
reader、installer、schema/权限与测试；当前源码仍强制逐列核对已实现的来源镜像。

采用前必须用实际所选 SQLite JDBC 驱动与文件系统证明：

- 目标明确使用 `journal_mode=DELETE`、`synchronous=FULL`、`foreign_keys=ON`，每个连接
  初始化并读回配置；不依赖 WAL，不能仅因设置调用成功而宣称平台耐久语义已验证。
- 每个连接的外键、约束和事务配置生效；UUID/二进制、精确数值、Unicode 与规范排序保持
  领域语义；MySQL 的 `FOR UPDATE`、列型、CHECK 和触发器不能机械照搬。
- 单写入者、目录排他锁、并发页面和旧运行请求的拒绝边界；busy/锁超时与取消有稳定结果，
  事务所有者独占提交/回滚，业务叶仓储不改变事务。
- 初始化及命令的各写入点、commit 响应丢失、回滚/关闭失败、进程终止和重启；不会发布
  半套快照、重复消费资源或通过新请求重做未决操作。
- 选定 rollback journal 模式与持久化设置、热 journal、磁盘满/权限失败、真实文件发布/读回、
  整目录清理和容量峰值；不能复制一个打开中的主数据库文件就声称备份完整。
- 每个存储模块的严格文件投影、独立覆盖、直接恢复与引用闭包，以及完整运行在来源断开时
  的继续/保存。代理 JDBC、自编内存往返和旧 MySQL 测试不能替代这些验证。

在上述门及完整领域闭包通过前，不开放 SQLite Host 运行，也不宣称完整战役文件可恢复。

## 版本与摘要

| 标识 | 负责什么 |
|---|---|
| `module_key` + `release_version` | 单个模组的准确发布身份；版本是字符串，不取最大值或做模糊比较 |
| 现行 `content_sha256` | 现行单发布规则逻辑投影的规范摘要，按既有合同与独立批准值一致 |
| `canonical_format_version` | 规则规范字节编码；不等于物理表结构 |
| `archive_format_version` | 产品存档协议 |
| 作者 schema / 安装清单版本 | 作者输入及制品清单的协议 |
| 当前两侧 `schema_version` | 各自 MySQL 数据库迁移链；目标 SQLite 另有应用初始化/存储模块协议 |
| `installation_revision` | 某来源发布根的安装代次，不能代替规则发布版本 |
| `row_version` / Host epoch | 业务并发与请求安全代次，不进入规则内容身份 |

原型的支持范围是当前应用版本，见[产品说明](../../product.md#原型阶段的版本范围)。记录准确
规则版本、组合和文件协议用于当前版本内的正确解释，不承诺保留旧存档读取器、旧组合算法
或旧工作集结构；当前实现保留的历史格式路径与未来支持政策分别判断。

规则键和版本按精确 ASCII 比较；`"1"`、`"01"`、`"1.0"` 不同。显示名与包目录名不授信。
文件 raw SHA-256、安装清单摘要、WAR 摘要、请求指纹和业务源状态指纹各有职责，不能代替
完整规则 canonical 摘要。清单自洽或安装成功均不能产生应用的发布批准。

新组合的原始 ZIP、模组逻辑、组合配置、最终规则和完整覆盖链五类摘要职责见公共基线。
它们分别核验制品、输入、准确有序组合、最终内容与解释过程；不复用现行持久化摘要域。
`content_sha256` 或相同最终规则内容都不能代替完整战役规则组合绑定；当前 canonical 2
及格式 2 内部单模组字段尚未采用这一合同。

## 安装、分区与发布

既有 schema 1 来源安装器只安装固定 `dnd5e2014_srd51_se` release `"1"` 的语言与工具
熟练 DRAFT 材料，先锁永久安装控制行，再锁发布根。
领域写入、头代次/观测摘要、安装事实、分区集合和计数同事务提交；永久操作身份支持对
原意图的查证，不通过换请求键绕过提交未知。已实现协议见[离线安装](../../rules/offline-language-installation.md)。

schema 2 当前使用独立原包和接受账本，与 schema 1 共用永久安装锁；来源 V003 及准确字段见
[来源账本](../../rules/schema-2-source-ledger.md)。原始 ZIP 是保管与复核制品，不把任意 JSON
属性袋用作业务规则表。当前逐领域来源镜像与运行快照按已实现合同接入；目标来源索引
职责与私有运行库须按前述采用门替换，不能在现有 reader 中静默省略所需行。
安装不自动接受，接受须绑定实际审阅的准确原包、逻辑摘要和协议；同一准确版本不替换原包。
当前完整基础和有领域声明/修改的包仍被机制资格门拒绝，不能从有限制品解析推导运行支持。

`PARTITION` 只证明已知分区，不能冒充全规则摘要、运行资格或 `COMPLETE`。`COMPLETE`
也不等于 `RELEASED`；仍需独立批准、全量重算及跨领域发布门。当前运行语言 Repository
仅接受 DRAFT PARTITION；未来完整快照使用新的身份对一次建立，不能原地把语言快照升级。

正式执行仍须满足受支持的机制、协议及发布资格。现行 built-in 独立批准路径不等于未来
自定义模组的离线校验、安装与 DM 对准确内容的接受路径；schema 2 的维护入口按公共基线
分离这些职责，安装成功或接受单个模组均不代替实际组合校验。身份注册表可以记载 DRAFT
以准确拒绝请求，生产加载器不据此执行 DRAFT。隔离测试不增加 Host 绕过发布门的开关；
完整 SRD release 1 仍为 DRAFT，canonical/archive 目标为 2/2，archive format 2 未正式激活；
legacy v1 保持默认 RELEASED。
当前内建目录不因未引用的 DRAFT 内容错误而加载它；当前 schema 2 来源 reader 则按已实现
账本范围核验全部制品和镜像。来源不可用的目标运行边界见前文，不能把共享来源检查继续
放在已初始化私有运行的命令入口。

当前仍支持的 RELEASED 身份须与其已接纳内容及安装事实一致；保留的真实事实不可重新
解释。这不承诺后续应用继续读取旧存档或旧规则制品。DRAFT 开发安装按
[迁移合同](../../database.md#迁移合同)选择保留数据库并前向演进，或采用新的初始化结构
并在明确授权后重建；观察摘要单独记录，不建立旧草稿兼容版本群。正式作者原包、离线
安装类和来源迁移 SQL 不进入 WAR；当前运行代码及所需迁移、读取/验证代码与独立批准
元数据按现行打包合同交付。目标应用自有的封闭存储清单与固定 SQLite 结构 SQL 模块随
应用交付，属于受审实现资源，不能与外部来源包或来源维护 SQL 混为一类。

  必须作为替代采用计划实现并验证，不能由仓储使用 `Connection` 接口推断已兼容。
