# 静态规则目录与运行数据库分离设计

本文定义规则目录与权威运行状态的目标边界。当前实现仍使用 `dnd_tool_se` 单一 schema 和
`java:comp/env/jdbc/DndToolSE`；本文不表示已经创建第二个数据库、执行迁移或改变部署配置。
当前自动化采用的运行、集成测试、迁移演练 schema 及账号矩阵以[数据库说明](database.md)为准，
它不提前创建 `jdbc/DndToolRules` 或物理规则库。任何分离实施都必须使用新的前向迁移和独立授权的
数据库、配置及部署检查点。

## 目标

- 将内置、版本化、经过摘要验证的规则目录与可变战役状态分开管理；
- 应用启动时完整加载并验证所需规则发布版，运行期只使用不可变内存快照；
- 运行事务不依赖规则目录的可变读取，也不引入跨数据库分布式事务；
- 规则发布版继续按稳定身份和内容摘要冻结，旧战役始终使用原发布版；
- 为后续角色、装备、战斗、法术、怪物和魔法物品目录提供统一加载边界。

本设计不增加规则上传、热重载、运行时脚本、动态 DDL、公开规则 API 或第三方模组安装。

## 当前边界

当前 `module_release`、`module_*`、`module_catalog_*_v2` 与战役、角色、事件和幂等表位于同一
schema。运行表广泛保存 `module_release_id`，部分表通过外键直接引用规则定义；战役创建和存档
确认也会在业务流程中读取规则目录。V001—V018 是不可修改的历史，因此不能通过移动旧表、改写
旧迁移或重新解释数据库 ID 来实现分离。

## 目标组件

### 规则目录存储

规则目录存储只包含：

- 规则发布身份、状态、canonical/archive 格式和 SHA-256；
- 类型化定义、属性、关系和受审核算法身份；
- 规则 schema 版本及规范迁移记录；
- 计算 canonical 摘要所需的完整逻辑投影。

规则运行账号只有 `SELECT`。新增或发布规则只能在停服、审核和备份边界内由独立 migrator
执行。`RELEASED` 行不可原地修改；新规则使用新发布身份或版本。只要运行数据库仍有战役引用，
对应规则发布版就不得删除。

### 运行数据库

运行数据库保存：

- 战役及其冻结的规则身份和内容摘要；
- 角色、物品、地图、战斗、法术、资源和状态；
- 根事件、快照、字段/资源变化、乐观版本和幂等结果；
- 运行数据库自己的发布绑定代理身份（如 schema 仍需要本地外键）。

跨边界权威身份是 `(module_key, release_version, content_sha256)`。规则目录数据库的自增 ID
不得写入存档，也不得被假定与运行数据库的本地 ID 相同。

### 不可变规则注册表

应用进程持有不可变的 `VerifiedRuleCatalogRegistry`，按规则身份和摘要精确索引
`ModuleCatalog`。注册表只在应用启动期间构建；Servlet 和业务 Service 只能读取已发布的完整
快照，不能自行查询、替换或扩张目录。

DRAFT 可以由测试或显式开发入口加载，但不得进入正式战役绑定、released dispatcher 或默认
发布选择。

## 启动加载协议

在应用开始接受 Host 请求前执行以下步骤：

1. 从运行数据库读取默认发布身份和所有既有战役引用的规则身份/摘要；
2. 通过只读规则连接，在一个 repeatable-read 快照中读取全部所需目录分区；
3. 拒绝未知、重复、畸形、未发布或应用不支持的身份、格式和算法；
4. 重新计算 canonical 字节和 SHA-256，并同时比较规则库记录、应用 manifest 与运行库冻结摘要；
5. 确认每个运行库引用都能解析为唯一、摘要一致的规则发布版；
6. 只有全部验证成功后才一次性发布不可变注册表并开放 Host 请求。

任一步失败都必须使规则相关能力失败关闭；不能回退到数据库最大版本、默认版、旧缓存或
canonical format 1。规则数据库在应用运行期间即使发生外部变化，也不能改变当前进程已经发布的
注册表；采用新规则必须经过停服、验证和重启，不提供热重载。

规则目录不是可变业务状态。把已验证目录保存在 JVM 不改变战役、角色、事件和幂等结果仍以运行
数据库为唯一权威来源的合同。

## 运行命令与事务

每个规则命令仍须：

1. 从运行事务读取并锁定战役、目标集合、版本、事件尾和冻结规则身份；
2. 以 `(module_key, release_version, content_sha256)` 精确解析不可变目录；
3. 在消耗随机性前验证完整请求、目录、目标状态和预览摘要；
4. 在单一运行数据库事务中提交状态、事件、审计、版本和幂等结果，或整体回滚。

规则注册表不参与提交，不要求 XA 或两阶段提交。需要调用方事务的 Repository 仍不得 commit 或
rollback。存档确认必须在运行事务内再次比较冻结身份和不可变注册表摘要，而不是依赖预览时保存的
可变对象引用。

## JNDI 与账号边界

现有 `java:comp/env/jdbc/DndToolSE` 保持为运行数据库合同。实施时可以新增而不能重命名该资源：

- `java:comp/env/jdbc/DndToolSE`：运行状态最小 DML；
- `java:comp/env/jdbc/DndToolRules`：规则目录只读加载。

第一阶段两个 DataSource 可以指向同一 schema，但必须使用不同职责的账号，以先建立代码、权限和
测试边界。物理拆分后，`jdbc/DndToolRules` 可以指向同一 MySQL 实例的独立 schema。除非另行设计
跨实例完整性、备份和故障恢复，不使用第二个 MySQL 实例。

口令继续只存在于 WAR 外的 Tomcat 配置。规则 migrator、运行 migrator、应用运行账号和只读核验
账号保持分离。

## 外键与物理拆分

历史运行表对本地规则表的外键继续受保护，不能为制造“干净拆分”而删除历史数据或改写旧迁移。
物理拆分必须通过新的前向迁移逐表处理：

- 先引入稳定发布绑定和应用级目录校验；
- 对 DRAFT 运行模型优先使用稳定规则键和本地发布绑定，不传播外部数据库 ID；
- 需要保留数据库级成员关系时，可以使用同一 MySQL 实例的跨 schema 外键，或经过摘要验证的
  本地只读键清单；不能维护两个可独立漂移的完整规则副本；
- RELEASED v1 的既有表、身份和解释必须继续可用；
- 删除旧规则表或外键不是首个分离切片的验收条件，且只能在证明没有发布/持久化合同受损后另行审核。

跨 schema 外键会使规则 schema 在运行期仍是数据库完整性依赖，因此它是“静态且只读”，不是可
随时卸载的数据库。若未来要求规则数据库在启动后可离线，必须另立设计，用运行库本地约束替代所有
跨 schema 外键。

## 迁移、发布与回滚

- V001—V018 保持原位置和原摘要；分离变更从下一个可用 V### 开始；
- 规则 schema 使用独立、明确的迁移清单和诊断，不复用或重新编号运行库历史；
- 安装规则目录、验证规则摘要、部署应用支持和允许新战役绑定是不同检查点；
- 先安装向后兼容的规则发布版，再部署能够识别它的应用；默认切换只发生在统一发布门；
- 应用回滚必须仍能加载所有既有战役引用的发布版；
- 数据库备份必须覆盖运行库以及所有被引用的规则发布版，不能只备份当前默认目录。

物理 schema 创建、数据复制、外键迁移、账号授权和真实规则加载均属于外部数据库操作，不能由
普通应用启动自动执行。

## 存档边界

存档继续只记录稳定规则身份、版本、内容摘要和业务状态，不记录规则数据库 ID、JNDI 名、数据库名
或连接信息。导入流程必须：

- 严格识别 archive 格式；
- 从不可变注册表解析完全相同的规则身份和摘要；
- 在接触运行数据库前完成第一次目录和载荷验证；
- 在确认事务中再次验证运行绑定和摘要；
- 对缺失规则发布版、摘要漂移或不支持格式失败关闭，且不留下部分状态。

规则目录本身不复制进每个战役存档；部署和数据库级备份必须确保旧发布版可恢复。

## 验证要求

聚焦测试至少覆盖：

- 正常启动加载多个发布版和只加载被引用/默认发布版；
- 规则库不可用、目录缺失、重复、畸形、未知算法、未发布状态和摘要不一致；
- 运行库引用缺失规则版及旧战役继续解析旧发布版；
- 注册表不可变、输入集合不可修改、外部规则行变化不影响已启动进程；
- 并发启动只发布一个完整快照，不暴露部分加载目录；
- 命令在随机性和任何写入前拒绝身份/摘要漂移；
- 存档预览与确认使用同一规则身份，失败回滚且 Repository 不越权提交；
- 两个 DataSource 的连接状态恢复、超时、只读属性和最小授权；
- 运行 schema 与规则 schema 的独立版本诊断和错误映射。

实现后先运行目录加载和事务定向测试，再运行 `mvn clean verify`。生产代码、JNDI 声明或打包资源
变化时执行 WAR 内容和敏感文件审计；真实数据库迁移、授权、部署和浏览器业务写入仍需分别授权。

## 实施切片

1. **不可变加载边界**：增加 `RuleCatalogProvider`/注册表及启动失败关闭测试，目录仍来自当前
   schema；业务 Service 不再各自创建 JDBC 目录 Repository。
2. **双 DataSource 与最小权限**：新增只读规则 JNDI，保留运行 JNDI；存档确认改用不可变目录并
   保持单一运行事务。
3. **稳定发布绑定**：通过前向迁移消除新 DRAFT 运行模型对外部规则数据库 ID 的依赖，完善诊断和
   archive 往返。
4. **物理 schema 分离**：在备份和回滚边界内复制并验证规则目录，逐步切换规则 DataSource；旧
   RELEASED 数据和仍需的本地约束保持可用。

每个切片单独评审和验证。完成早期切片不表示规则数据库已物理迁移，也不触发完整规则族发布、
archive format 2 激活或新战役默认切换。
